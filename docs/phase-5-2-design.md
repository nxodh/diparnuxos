# 0.5.2 설계: 경량화, 설치기 수정, 제어 센터 개편

- 확인 날짜: 2026-10-13
- 상태: **설계 초안. 구현 중이다.** 아래 "확인한 사실"은 0.5.1 이미지를 QEMU(가속 없음, 4 GiB)에서 실행해 잰 값과 컨테이너 실험이다. 실기 값이 아니다.

0.5.2 는 세 가지를 한 버전에 담는다.

1. 설치기 수정(비밀번호 사전 검사, `sudo` 그룹) — **완료**
2. 경량화(측정 → 줄이기 → 새 램 목표)
3. 제어 센터 개편: 모델 관련 기능을 제어 센터에서 빼고, 네트워크·서버·원격 접속 기능을 강화한다

## 2. 확인한 사실

### 2.1 메모리 측정(0.5.1 ISO, QEMU, 라이브 세션, 4 GiB, 가속 없음)

사용 메모리는 `MemTotal − MemAvailable` 이다. PSS 는 프로세스별 `smaps_rollup` 의 합이다(공유 페이지를 나눠 센다).

| 상태 | 사용 메모리 | 사용자 영역 PSS | 커널·tmpfs·기타 |
|---|---|---|---|
| 서버 모드 | 361 MiB | 76 MiB | 284 MiB |
| 데스크톱, 세션만(Control Center 끔) | 565 MiB | 375 MiB | 189 MiB |
| 데스크톱 + Control Center | 653 MiB | 506 MiB | 146 MiB |

데스크톱 세션만의 주요 항목(PSS): Xorg 110 MiB, 패널 플러그인 래퍼 6개 47 MiB, `xfce4-session` 39 MiB, `diparnuxd` 34 MiB(서버 모드는 12 MiB), `xfdesktop` 18 MiB, `systemd` 10 MiB, `xfce4-panel` 9 MiB, `xfwm4` 9 MiB, PipeWire 계열 약 12 MiB.
서버 모드에서도 PipeWire·WirePlumber·pipewire-pulse 가 약 18 MiB(PSS) 상주한다.

이 측정은 라이브 세션이라 "기타"에 오버레이와 페이지 캐시가 섞여 있다. 설치된 시스템의 기준선은 별도로 잰다(5절).

### 2.2 Control Center 렌더러 실험(Xvfb, 소프트웨어 GL, 컨테이너)

| 설정 | PSS |
|---|---|
| 기본(GSK 자동 선택) | 295 MiB |
| `GSK_RENDERER=gl` | 249 MiB |
| `GSK_RENDERER=cairo` | 168 MiB |
| 빈 libadwaita 창(앱 코드 없음) | 167 MiB |

`GSK_RENDERER=cairo` 가 127 MiB 를 줄인다. 앱 코드는 바닥(167 MiB) 위에 거의 아무것도 더하지 않는다. 바닥은 Python, GTK4, libadwaita 의 몫이다.

### 2.3 설치기

- Calamares 3.3.14 의 사용자 모듈은 `sudoersGroup` 으로 `/etc/sudoers.d/10-installer` 에 `%sudo ALL=(ALL) ALL` 만 쓰고 계정을 그 그룹에 넣지 않는다. 계정이 그룹에 들어가려면 `defaultGroups` 에 적어야 한다.
- 이미지에는 cracklib 사전이 없어서 사전 검사를 켠 채로는 모든 비밀번호가 "error loading dictionary" 로 거절된다. `dictcheck=0` 으로 해결했다.

## 3. 경량화

램 목표는 측정 뒤에 정한다. 이번 단계에서 효과가 확인되었거나 기대되는 항목이다.

| 번호 | 항목 | 근거 | 예상 효과 | 위험 |
|---|---|---|---|---|
| L1 | Control Center 를 `GSK_RENDERER=cairo` 로 실행 | 2.2 | −120 MiB(소프트웨어 GL 일 때) | 설정 앱이라 영향이 작다. 확인: 화면 캡처 |
| L2 | `diparnuxd` Go GC 조정(`GOGC`, `GOMEMLIMIT`) | 12 → 34 MiB 증가 | −10~20 MiB | 지연 시간은 영향이 작다 |
| L3 | 서버 모드에서 PipeWire 계열 미기동 | 2.1 | −18 MiB(서버 모드) | 데스크톱에서는 그대로 기동해야 한다 |
| L4 | 패널의 `actions` 플러그인 제거 | 래퍼 하나 약 8 MiB | −8 MiB | 종료·잠금은 시작 메뉴에 있다 |
| L5 | Xorg 2D 가속 끄기 후보(`AccelMethod none`, 가상 머신 한정 검토) | Xorg 82~110 MiB | 수십 MiB | 실기 성능 영향. 실험 뒤 결정 |
| L6 | 설치된 시스템의 기준선 측정 | 2.1 의 한계 | 새 목표의 기준 | |

적용 순서: L1, L2, L3, L4 를 먼저 하고 재측정한다. L5 는 가상 머신 실험 뒤에 결정한다. 새 목표는 재측정 값을 바탕으로 `docs/memory.md` 에 적는다.

기능 추가와 경량화는 충돌한다. 새 서비스(원격 데스크톱, VPN, 웹 관리)는 **기본으로 꺼 두고**, 켤 때만 프로세스가 뜬다. 켜지 않은 상태의 상주 비용은 0 에 가깝게 유지하는 것을 수용 기준으로 둔다(8절).

## 4. 제어 센터 개편

### 4.1 페이지 구성

| 이전 | 이후 |
|---|---|
| 대시보드 | **대시보드**(GPU 정보는 유지, 자원 요약 추가) |
| 모델 | 제거(모델 기능은 CLI 와 API) |
| 서버(llama 시작·정지·계획) | 제거 → **원격 접속**(SSH, 원격 데스크톱, VPN, 웹 관리) |
| 채팅 | 제거 |
| 네트워크(Wi-Fi) | **네트워크**(유선, 고정 IP, DNS, 호스트 이름, 진단, Wi-Fi) |
| 시스템(계정, SSH, 모양) | **시스템**(계정, 모양, 첫 설정) |
| — | **방화벽**(규칙 관리) |
| — | **서비스**(목록, 제어, 로그) |
| — | **자원**(CPU, 메모리, 디스크, 네트워크, GPU) |

모델 기능을 빼면 첫 부팅 마법사의 모델 단계도 정리해야 한다(`wizard.py`, 6단계 중 모델 추천·다운로드 단계).

### 4.2 구조

새 기능은 같은 패턴으로 만든다.

- 데몬(`diparnuxd`)에 `/v1/...` 엔드포인트를 더한다. 소켓 권한은 기존과 같다(그룹 `diparnux` 구성원만).
- 데몬은 `ProtectSystem=full` 이라 `/etc` 에 쓸 수 없다. 설정을 쓰는 일은 **권한이 있는 헬퍼**가 한다. 계정 관리(`diparnux-user`)에서 쓰던 `systemd-run --pipe` 방식을 따르되, 새 기능은 셸이 아니라 Go 헬퍼 하나(`diparnux-admin`, 하위 명령별 JSON 입출력)로 만들어 단위 시험이 쉽게 한다.
- CLI(`diparnux ...`)와 제어 센터는 같은 API 를 쓴다. 기능마다 CLI 가 먼저 있고 화면이 그 위에 올라간다.
- **잠금 방지**: 네트워크, 방화벽, SSH 설정을 바꾸면 접속이 끊길 수 있다. 위험한 변경은 "적용 후 60초 안에 확인하지 않으면 이전 설정으로 되돌린다"(확인 또는 자동 복구)를 기본으로 둔다.

### 4.3 기능별 설계

| 기능 | 내용 | 구현 요점 |
|---|---|---|
| 방화벽 규칙 | 규칙 = 이름, 프로토콜(tcp/udp), 포트 또는 범위, 출발지(모두, LAN, CIDR), 사용 여부. 지금의 암묵 규칙(API 포트, SSH 포트)을 이 모델로 옮긴다. 기본 정책은 차단 | `table inet diparnux` 생성기(`internal/firewall`)를 규칙 목록 입력으로 확장. `nft -c` 로 검증하고 원자적으로 적용, 자동 복구 |
| SSH 고급 | 공개 키 등록·삭제(계정별 `authorized_keys`), 포트 변경, 비밀번호 로그인 허용 여부, 접속 허용 사용자, 최근 접속 기록 | `sshd_config.d` 조각을 헬퍼가 쓴다. `sshd -t` 로 검증하고 실패하면 되돌린다. 포트 변경은 방화벽 규칙과 함께 바꾼다 |
| 유선·고정 IP·DNS·호스트 이름 | 인터페이스별 DHCP 또는 고정(주소, 게이트웨이, DNS), 호스트 이름 변경, 진단(핑, 경로, 이름 확인) | `systemd-networkd` 의 `.network` 조각과 `resolved`, `hostnamectl`. Wi-Fi 는 iwd 와 networkd 를 그대로 쓴다 |
| 원격 데스크톱 | 다른 컴퓨터에서 Xfce 화면에 접속(RDP) | 후보: `xrdp`(+`xorgxrdp`). 이미지에 넣되 기본으로 꺼 둔다. 켜면 서비스와 방화벽 규칙(TCP 3389)을 함께 켠다. 결정 필요(9절) |
| 서비스 관리와 로그 | 서비스 목록, 시작·정지·재시작·부팅 때 시작 설정, 서비스별 로그(줄 수 제한) | 읽기는 전체. 제어는 허용 목록(`diparnux-*`, `ssh`, `xrdp`, `wg-quick@*`, `lightdm`, `systemd-networkd`, `iwd` 등)만 |
| 자원 모니터링 | CPU, 메모리, 디스크, 네트워크 처리량, 온도, GPU(NVML) | 상주 수집기를 두지 않는다. API 를 부를 때마다 `/proc`, `/sys` 를 읽고 화면이 열려 있는 동안만 주기적으로 요청한다(경량화 원칙) |
| WireGuard VPN | 인터페이스 생성(키 생성), 피어 추가(공개 키, 허용 IP, 엔드포인트), 상태 보기, 켜기·끄기 | `systemd-networkd` 의 `.netdev`/`.network`(WireGuard). 개인 키는 root 만 읽는 파일에 저장하고 API 로 돌려주지 않는다. UDP 포트 방화벽 규칙을 함께 연다 |
| 원격 관리 웹 페이지 | 다른 컴퓨터의 브라우저에서 같은 관리 화면을 본다 | 데몬이 TLS(자체 서명 인증서) 리스너를 따로 열어 정적 페이지와 같은 API 를 제공한다. 기본으로 꺼 둔다. 인증은 웹 관리 전용 비밀번호(argon2id 해시)와 세션 토큰, 시도 횟수 제한. 가장 큰 작업이므로 마지막에 한다 |

### 4.4 보안 원칙

- 새 기능은 **기본으로 꺼 둔다**. 켜기 전에는 포트가 열리지 않고 프로세스가 뜨지 않는다.
- 비밀번호, 개인 키, 토큰은 로그와 응답에 남기지 않는다. 설정 파일은 root 만 읽게 쓴다.
- 포트를 여는 기능은 방화벽 규칙 하나와 묶여 있고, 규칙 화면에서 보인다.
- 원격 관리 웹과 원격 데스크톱은 LAN 공개를 따로 켜야 한다(기본은 이 컴퓨터에서만 접속).

## 5. 모델 가져오기

`diparnux model import <파일> [--name N]`: 파일을 모델 폴더로 복사하고 SHA-256 을 계산해 메타데이터(`repo=local`, `revision=manual`, `license`)를 쓴다. 외부에서 받은 GGUF 를 쓰는 길이다.
지금은 `/var/lib/diparnux/models` 에 파일과 `<이름>.gguf.json`(`repo`, `revision`, `sha256`, `license`)을 직접 넣어도 된다. 이 파일이 없으면 모델이 완전하지 않은 것으로 표시되어 제어 센터의 선택 목록에 나오지 않는다.

## 7. 시험 계획

- 단위: 방화벽 규칙 생성(고정 출력 비교), 네트워크 조각 생성, SSH 조각 검증, WireGuard 키 비공개성, 서비스 허용 목록, 지표 파싱.
- 컨테이너: 실제 `nft -c`(규칙 문법), `sshd -t`, `networkd` 조각 문법(`systemd-analyze verify`) 검사.
- GUI: 가짜 데몬으로 각 페이지 생성·동작, 번역 누락 검사.
- QEMU E2E: 정적 IP 변경 후 복구(자동 복구 포함), 방화벽 규칙 추가 후 포트 접속, SSH 키 로그인, WireGuard 인터페이스 생성, 서비스 제어, 지표 응답, 원격 관리 웹 로그인(`curl`).
- 경량화: 변경 전후의 프로세스별 PSS 와 사용 메모리를 같은 시나리오로 비교한 표를 검증 기록에 남긴다.

## 8. 수용 기준

1. 제어 센터에 모델, 서버(llama), 채팅 페이지가 없고 `diparnux model`, `diparnux serve` 는 그대로 동작한다.
2. 기능을 켜지 않은 상태에서 새 서비스 프로세스(원격 데스크톱, VPN, 웹 관리)가 뜨지 않고 열린 포트가 늘지 않는다(`ss -ltnu` 비교).
3. 네트워크, 방화벽, SSH 변경이 확인되지 않으면 자동으로 이전 설정으로 돌아온다.
4. 경량화 L1~L4 를 적용한 재측정 값이 2.1 보다 작다. 새 램 목표는 그 값을 바탕으로 정한다.
5. 모든 새 기능은 CLI 로도 쓸 수 있다.
6. 기존 시험(CI 전체)이 통과한다.
