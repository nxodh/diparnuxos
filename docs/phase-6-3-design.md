- 확인 날짜: 2026-10-14
- 상태: **설계 확정 대기(구현 전).** 사용자 요청 5가지를 코드와 컨테이너 재현으로 조사한 결과와 계획이다. 사용자 결정 6건은 2026-10-14 에 받았고 8절에 적었다. 부팅 문제는 사용자 PC 의 `efibootmgr` 결과(1.2절)로 일부 좁혀졌고, BIOS 화면에 대한 추가 정보(1.3.1절)가 남았다.
- 배경: 0.6.2 를 실제 PC(한 SSD 에 Windows 10 과 함께 설치)에 설치해 본 사용자의 보고다. 0.6.2 의 디자인과 설치 검증은 가상 환경(Xvfb 컨테이너, QEMU)에서만 했다. 아래 문제 대부분은 그 환경에서 드러나지 않았다. 이것은 검증 범위의 한계였고, 0.6.3 은 **실기 확인을 완료 조건**에 넣는다(7절).

## 1. 부팅 항목이 BIOS 에 보이지 않는 문제

### 1.1 코드에서 확인한 사실

`daemon/internal/install/configure.go` 의 `InstallBootloader`(Calamares 의 `opereta-bootloader` 단계가 부른다):

1. `grub-install --target=x86_64-efi --efi-directory=/boot/efi --bootloader-id=opereta --uefi-secure-boot` 로 NVRAM 항목 `opereta` 를 만든다.
2. **실패하면** `--no-nvram` 으로 파일만 설치한다. 이때 사용자에게는 "등록 실패" 이벤트 한 줄이 남을 뿐이고 설치는 **성공으로 끝난다**. 부팅 항목이 없는 채로 설치가 끝날 수 있다.
3. 이어서 `--removable` 로 `EFI/BOOT/BOOTX64.EFI` 에 한 번 더 설치한다. **Windows 가 같은 ESP 를 쓰면** 이 경로의 기존 파일을 덮어쓴다(Windows 의 대체 부팅 파일일 수 있다).
4. `update-grub` 뒤 저장된 기본 항목을 고정한다.

그 밖에:

- **UEFI 모드로 부팅했는지 확인하지 않는다.** `docs/installation.md` 는 "BIOS 는 지원하지 않는다"고 쓰지만 설치기 어디에도 `/sys/firmware/efi` 검사가 없다. 설치 USB 를 레거시(CSM) 모드로 부팅하면 Calamares 는 정상처럼 진행하고 `grub-install --target=x86_64-efi` 는 실제 ESP 가 아닌 곳(`/boot/efi` 일반 디렉터리)에 쓰거나 NVRAM 에 쓰지 못한다.
- **`os-prober` 가 이미지에 없다.** GRUB 메뉴에 Windows 가 나오지 않는다. 즉 BIOS 부팅 순서에서 Windows Boot Manager 가 앞서면 Opereta 에 갈 방법이 없고, GRUB 이 앞서면 Windows 로 가는 방법이 없다.
- **시험이 이 문제를 걸러내지 못한다.** `tests/qemu/install.py` 는 빈 디스크에 설치하고, Secure Boot 를 켠 채 **대체 경로 `EFI/BOOT/BOOTX64.EFI` 로** 부팅한다. NVRAM 항목(`efibootmgr -v`)은 단언하지 않는다. Windows 가 있는 디스크, 기존 ESP 재사용, NVRAM 쓰기 실패는 시험한 적이 없다.
- 설치 끝 화면과 설치된 시스템 어디에도 "부팅 항목이 정말 있는지"를 확인하거나 보여 주는 곳이 없다.

### 1.2 사용자 PC 에서 수집한 결과(2026-10-14, 사진 T01)

사용자가 설치된 시스템의 터미널에서 안내한 명령(`ls /sys/firmware/efi`, `efibootmgr -v`, `lsblk`, `find /boot/efi`)을 실행한 사진이다(글자 인식 결과라 일부 값은 불확실하다). 읽을 수 있었던 사실:

| 항목 | 값 | 의미 |
|---|---|---|
| 부팅 모드 | **UEFI** | 레거시로 설치한 것이 아니다 |
| `BootCurrent` | `0000` (= opereta) | 지금은 Opereta 항목으로 부팅한 상태다 |
| `Boot0000 opereta` | `HD(1,GPT,…)/File(\EFI\OPERETA\SHIMX64.EFI)` | **NVRAM 항목은 있다**(등록 실패가 아니다) |
| `Boot0001 Windows Boot Manager` | `\EFI\MICROSOFT\BOOT\BOOTMGFW.EFI` | Windows 항목, 같은 ESP(파티션 1) |
| `Boot0002 UEFI: SanDisk` | USB | 설치 USB |
| **`BootOrder`** | **`0002, 0001, 0000`** | **Opereta 가 맨 마지막이다.** USB, Windows, Opereta 순 |
| 디스크 | NVMe 953.9 GB: p1 100M vfat(ESP, `/boot/efi`), p2 16M(Microsoft 예약), p3 463G **BitLocker**, p4 597M ntfs(복구), p5 10G **BitLocker**, p6 480G ext4(Opereta) | ESP 는 **하나**이고 Windows 와 공유한다. Windows 는 **BitLocker 로 암호화**되어 있다 |
| ESP 내용 | `EFI/Boot/`(bootx64.efi, grubx64.efi, mmx64.efi, grub.cfg, BOOTX64.CSV), `EFI/opereta/`(shimx64, grubx64, fbx64, mmx64, grub.cfg), **`EFI/diparnux/`**, `EFI/Microsoft/` | `EFI/Boot` 는 우리 `--removable` 설치다. **이전 이름 Diparnux 의 폴더가 남아 있다**(이 PC 에 이전 버전을 설치한 적이 있다) |
| 화면 아래 시계 | `2000-04-13` | **시스템 날짜가 틀렸다**(RTC 가 초기화되었거나 설치기가 시각을 못 맞췄을 수 있다) |

사진에 없는 것: Secure Boot 상태, 두 번째 사진(T02, 글자를 읽지 못함).

### 1.3 원인 후보와 판정(수집한 정보 기준)

| 후보 | 판정 | 근거 |
|---|---|---|
| H1 NVRAM 쓰기 실패 | **배제** | `Boot0000 opereta` 가 있다 |
| H2 레거시 모드로 설치 | **배제** | UEFI 로 부팅했다 |
| H3 ESP 가 둘 | **배제** | ESP 는 p1 하나다 |
| H4 순서를 Windows 가 앞세움 | **유력** | `BootOrder` 에서 Opereta 가 맨 뒤다. Windows(또는 펌웨어)가 순서를 다시 쓴 것으로 보인다. 설치 직후에는 앞이었는지 알 수 없다 |
| H5 Secure Boot | 미확인 | 값이 없다 |
| H6 (새) 펌웨어의 목록 표시 방식 | **미확인, 가능성 있음** | 항목이 있는데도 BIOS 화면에서 "파티션"으로 보이지 않는 것일 수 있다. UEFI 는 파티션이 아니라 **부팅 항목**(이름 `opereta`)을 보여 준다. BIOS 의 어떤 화면에서 어떻게 보이는지 확인이 필요하다 |

결론: **"항목이 아예 없다"는 가설은 틀렸다.** 항목은 있고, 순서가 뒤이며, BIOS 가 그 항목을 어떻게 보여 주는지가 남은 질문이다. 1.1절의 코드 결함(실패를 조용히 넘김, UEFI 확인 없음, os-prober 없음 등)은 실제로 있지만 이 PC 에서 일어난 일의 직접 원인은 아니다.

### 1.3.1 추가로 필요한 정보

- BIOS 의 **어느 화면**(부팅 순서, 부팅 메뉴(F12 같은 키), 부팅 장치 선택)에서 Opereta 를 찾았는지와 그 화면에 보이는 항목 이름들(사진). F12 같은 일회성 부팅 메뉴에 `opereta` 가 보이는지.
- PC 제조사와 모델(BIOS 화면의 이름), Secure Boot 상태.
- 사진 T02 의 내용(텍스트로 알려 주시거나 더 작은 파일로 다시 올려 주세요. 글자를 읽지 못했습니다).
- 설치할 때 고른 방식("나란히 설치", "수동" 등).

### 1.4 수정 계획

| 번호 | 변경 | 내용 |
|---|---|---|
| B1 | UEFI 확인 | 설치기 환영 단계에서 `/sys/firmware/efi` 가 없으면 이유와 해결 방법(UEFI 로 다시 부팅)을 보여 주고 진행을 막는다 |
| B2 | 항목 등록을 확인 | `grub-install` 뒤 `efibootmgr -v` 에 `opereta` 가 있는지 **확인한다**. 없으면 `efibootmgr --create --disk <디스크> --part <ESP 번호> --loader '\EFI\opereta\shimx64.efi' --label Opereta` 로 직접 만들고 다시 확인한다. 그래도 없으면 설치를 실패로 하지 않되 끝 화면에 **경고와 복구 방법**을 보여 준다(조용히 성공하지 않는다) |
| B3 | 대체 경로 보호 | `EFI/BOOT/BOOTX64.EFI` 가 이미 있고 우리 것이 아니면 덮어쓰지 않는다(Windows 와 공존). 없거나 우리 것이면 쓴다 |
| B4 | 기존 ESP 재사용 | 디스크에 ESP 가 이미 있으면 새로 만들지 않고 그것을 `/boot/efi` 로 쓰도록 안내하고 기본값으로 둔다(H3) |
| B5 | Windows 항목 | `os-prober` 와 `ntfs-3g` 를 넣고 `GRUB_DISABLE_OS_PROBER=false` 로 GRUB 메뉴에 Windows 를 올린다. 이미 Windows Boot Manager 가 앞서는 경우를 위해 B7 의 도구로 순서를 바꿀 수 있게 한다 |
| B6 | 진단 | `opereta boot status` 가 UEFI 여부, 항목, ESP 파일, 부팅 순서를 보여 주고 문제를 분류한다. 설치 끝 화면과 제어 센터(4절)가 같은 결과를 쓴다 |
| B7 | 복구와 순서 | `opereta boot repair`(grub-install 과 항목 만들기 다시), `opereta boot order`, `opereta boot next <항목>`(다음 한 번만). 제어 센터의 "부팅" 페이지가 같은 동작을 한다. 라이브 USB 에서도 설치된 시스템을 골라 복구할 수 있게 한다 |
| B9 | 부팅 순서 고정 | 설치 마지막에 Opereta 항목을 **맨 앞**으로 두고(`efibootmgr -o`), 설치된 시스템의 부팅 때마다 확인해 Windows 가 순서를 바꿨으면 알린다(제어 센터 "부팅" 페이지, `opereta boot status`). 사용자가 Windows 를 앞에 두기로 했다면 존중한다(설정으로 끌 수 있다). **BitLocker 주의**: 부팅 구성을 바꾸기 전에 BitLocker 복구 키가 있는지 안내한다(부팅 순서 변경이 보통 복구 키를 요구하지는 않지만 보장할 수 없다) |
| B10 | 이전 이름 폴더 | ESP 에 `EFI/diparnux`(이전 이름) 같은 옛 폴더가 있으면 목록에 보여 주고 **사용자 확인 뒤** 지울 수 있게 한다(자동으로 지우지 않는다). 옛 NVRAM 항목도 같다 |
| B11 | 시스템 시각 | 설치 직후 `2000-04-13` 처럼 틀린 시각이 나온 원인을 조사한다(`hwclock` 단계, RTC 가 UTC/로컬 중 무엇인지 — Windows 와 공존하면 RTC 를 로컬 시간으로 쓰는 문제가 있다). 시각이 틀리면 TLS 와 업데이트(릴리스 서명 검증)가 실패한다. 설치기에서 시각대와 RTC 모드를 정하고 첫 부팅에 네트워크 시각 동기화를 켠다 |
| B8 | 시험 | QEMU 에 (a) Windows 와 비슷한 ESP(`EFI/Microsoft/Boot/bootmgfw.efi`, `EFI/BOOT/BOOTX64.EFI`)가 미리 있는 디스크에 설치, (b) `efibootmgr -v` 로 `opereta` 항목 단언, (c) NVRAM 항목을 지운 뒤 대체 경로로 부팅과 `boot repair`, (d) 레거시 부팅 거절, (e) Windows 항목이 GRUB 메뉴에 있음을 추가한다 |

### 1.4.1 지금 할 수 있는 임시 조치(사용자 PC)

Opereta 를 기본으로 부팅하려면(Windows 는 BIOS 의 일회성 부팅 메뉴에서도 선택할 수 있다):

```sh
sudo efibootmgr -o 0000,0001,0002     # opereta, Windows Boot Manager, USB 순
```

BitLocker 가 켜져 있으므로 **복구 키를 확인한 뒤** 실행하세요(보통 필요 없지만 보장할 수 없습니다). 되돌리려면 `sudo efibootmgr -o 0001,0000,0002` 입니다.

### 1.5 한계

실제 펌웨어마다 NVRAM 동작이 다르다. 가상 펌웨어(OVMF)의 시험이 모든 PC 를 보장하지 않는다. 그래서 B2 의 확인과 B7 의 복구 도구가 핵심이다. 막지 못하는 경우에도 사용자가 스스로 고칠 수 있어야 한다.

## 2. 창 가장자리의 검은 선과 상자

### 2.1 확인한 사실

`scripts/make-theme.py` 가 만드는 GTK3 테마 CSS 에는 다음이 **조건 없이** 들어 있다.

```css
decoration { box-shadow: 0 6px 24px alpha(black, 0.28), 0 0 0 1px <테두리색>; }
window.csd, window.csd decoration { border-radius: 12px; }
```

GTK3 의 `decoration` 노드는 앱이 직접 그리는 창(CSD)뿐 아니라 **창 관리자가 장식하는 창(SSD)**, 최대화·타일 상태, 합성이 없는 화면에도 있다. Adwaita 는 `.ssd`, `.solid-csd`, `.maximized`, `.tiled`, `.fullscreen` 상태마다 그림자와 모서리를 끈다. 우리 CSS 는 이를 모두 덮어써서:

- 서버측 장식 창에서 1px 테두리와 그림자가 창 안쪽에 칠해진다 → **얇은 선**
- 합성 관리자가 꺼져 있거나 투명 시각(ARGB)을 지원하지 못하는 환경에서 그림자 영역이 불투명한 검은색으로 칠해지고 그 안에 둥근 창이 들어간다 → **검은 상자 안의 둥근 사각형**

이것은 사용자가 설명한 두 증상과 맞는다. 다만 Xvfb 컨테이너에서는 재현되지 않았다(합성이 정상 동작했고 GPU 경로가 없다). **실기에서 재현해야 확정한다.**

### 2.2 추가 위험

- 합성 관리자(xfwm4)가 켜지지 못하는 경우: `use_compositing` 은 켜 두었지만 `vblank_mode=auto` 가 GLX 를 고르다 실패하면 조용히 꺼진다. NVIDIA 드라이버가 있는 실기에서 흔하다. 꺼졌는지 사용자에게 알리는 곳이 없다.
- xfwm4 의 프레임은 우리가 만든 PNG 이미지 조각이다. 투명 모서리는 합성이 있을 때만 정확하다.

### 2.3 수정 계획

| 번호 | 변경 | 내용 |
|---|---|---|
| W1 | CSS 조건화 | 그림자와 모서리는 `window.csd:not(.maximized):not(.fullscreen):not(.tiled):not(.solid-csd) decoration` 에만 준다. `.ssd decoration`, `.solid-csd decoration`, 최대화는 그림자와 모서리를 끈다. CSD 창의 그림자는 `margin` 으로 영역을 명시한다 |
| W2 | 합성 상태 확인 | 세션 시작 때 합성이 실제로 켜졌는지(`_NET_WM_CM_S0` 소유자) 확인한다. 꺼졌으면 `vblank_mode` 를 `xpresent`/`off` 로 바꿔 다시 시도하고, 그래도 안 되면 합성이 없을 때 쓰는 **사각형 모서리 프레임**으로 자동 전환한다(검은 상자가 생기는 것보다 낫다) |
| W3 | 렌더링 방식 재검토 | 아래 5.3절의 합성 관리자 교체(picom)가 이 문제의 뿌리를 없앤다. 결정 D2 |
| W4 | 앱 목록 시험 | 시험 앱 모음: Thunar, Mousepad, Firefox, xfce4-terminal, 설정 관리자, pavucontrol, xarchiver, ristretto, Calamares(Qt), 제어 센터(GTK4), `gtk3-widget-factory`(CSD 기준), 대화 상자, 메뉴, 툴팁. 합성 켬/끔, 일반/최대화/타일 상태의 스크린샷을 비교한다 |
| W5 | 화면 검증 하네스 | 이번 조사에서 쓴 컨테이너 하네스(Xvfb, xfwm4, 패널, 앱 모음, 스크린샷)를 저장소에 넣어(`scripts/preview-desktop-in-docker.sh`) 회귀를 잡는다. 실기를 대체하지는 못한다 |

## 3. 창 상단 단추(x, −, +)가 앱마다 다른 문제

### 3.1 재현과 원인(확인)

컨테이너에서 `gtk3-widget-factory`(GTK3 CSD 앱)와 Firefox ESR 을 띄워 보았다.

- xfwm4 가 장식하는 창(Firefox 의 시스템 제목 줄 포함)의 단추는 우리 이미지라 x, −, + 가 맞다.
- **앱이 직접 그리는 제목 줄(CSD)의 최대화 단추는 □ 로 나온다.** 우리 `Opereta` 아이콘 테마에 `window-maximize-symbolic` 을 넣었지만 쓰이지 않는다.
- 원인: GTK3 의 아이콘 조회는 `window-maximize-symbolic` 등을 아이콘 테마보다 먼저 **라이브러리에 내장된 리소스 아이콘**(`/org/gtk/libgtk/icons/16x16/status/window-maximize-symbolic.symbolic.png`)에서 찾는다. GTK4/libadwaita(0.6.2 의 제어 센터)와 같은 현상이며, 제어 센터만 CSS 배경 이미지로 우회했고 GTK3 에는 적용하지 않았다.
- Firefox 는 설정에 따라 시스템 제목 줄(xfwm4)이나 자체 제목 줄(GTK 단추를 모방)을 쓴다. 사용자의 Firefox 는 후자라서 □ 가 보인 것이다.

### 3.2 수정 계획

| 번호 | 변경 | 내용 |
|---|---|---|
| T0 | **단추 순서 변경(사용자 결정)** | 순서를 **x(닫기), +(최대화), −(최소화)** 로 한다. 0.6.2 는 x, −, + 였다. xfwm4 `button_layout` 은 `CHM\|` → **`CMH\|`**, GTK `DecorationLayout` 은 `close,minimize,maximize:` → **`close,maximize,minimize:`**. 제어 센터(GTK4)는 같은 GTK 설정을 따르므로 함께 바뀐다. 시험: 레이아웃 문자열과 스크린샷에서 순서를 확인한다 |
| T1 | GTK3 CSS 로 단추 그리기 | `headerbar button.titlebutton`(`.close`, `.minimize`, `.maximize`)에 PNG 를 `background-image` 로 주고 내장 `image` 는 숨긴다. 제어 센터와 같은 자산(`ctl-*-light/dark.png`)과 같은 원형 배경을 쓴다. 단추 순서와 위치도 맞춘다(왼쪽, 닫기-최소화-최대화) |
| T2 | Firefox 기본값 | `policies.json` 으로 시스템 제목 줄(`browser.tabs.inTitlebar = 0`)을 기본으로 둔다(사용자가 바꿀 수 있게 `Preferences` 로 두고 잠그지 않는다). 시스템 제목 줄이면 xfwm4 가 그리는 단추라 항상 맞다 |
| T3 | 다른 CSD 앱 | GNOME 앱처럼 자체 단추를 그리는 앱은 T1 로 맞춘다. T1 이 닿지 않는 앱(자체 렌더러, Electron 등)은 한계로 문서에 적고 xfwm4 장식을 강제하는 방법(`GTK_CSD=0` 환경 변수)을 제공한다. 결정 D3 |
| T4 | 시험 | W4 의 앱 목록에서 최대화 단추 모양을 스크린샷으로 확인한다. T1 이 Firefox 의 CSD 단추에도 닿는지는 **구현 전에 확인할 항목**이다(닿지 않으면 T2 가 해결책이다) |

## 4. Opereta 제어 센터

### 4.1 현재

페이지 11개: 대시보드, 모델, 서버, 연결, Deberopa, 네트워크, 방화벽, 원격 접속, 서비스, 자원, 시스템. **모두 AI 서버 관리**이고, 데스크톱 컴퓨터로서의 설정(화면, 소리, 입력, 앱, 저장소, 부팅)은 Xfce 설정 관리자로 가야 한다. 시스템 페이지 하나에 모드, 계정, 상시 가동, SSH, 모양, 업데이트, 유지 관리가 섞여 있다.

### 4.2 계획: 설정의 중심으로

`macOS 시스템 설정` 처럼 **한 곳에서 컴퓨터 전체를 설정**하고, AI 서버 관련은 그 안의 한 묶음으로 **그대로 둔다**(사용자 결정 2026-10-14: AI 를 빼지 않는다). 왼쪽 사이드바를 묶음으로 나눈다.

| 묶음 | 페이지 | 비고 |
|---|---|---|
| 개요 | 홈(상태 한눈에: 서버, GPU, 업데이트, 경고), 이 컴퓨터(사양, 버전, 디스크, 가동 시간) | 새로 만듦 |
| AI | 대시보드, 모델, 서버, 연결, Deberopa, 자원 | 지금 있는 것을 정리(빼지 않는다) |
| 모양 | 외관(밝게/어둡게/자동, 배경 화면, 글꼴 크기, 아이콘, 창 효과), 독과 메뉴 막대(5절) | 새로 만듦 |
| 하드웨어 | 디스플레이(해상도, 배율, 다중 모니터, 야간 모드), 소리, **블루투스**(켜기/끄기, 검색, 페어링, 연결 해제, 기기 삭제), 키보드와 입력기(한/영 키, 자판), 전원, **그래픽(GPU)**: 드라이버, **CUDA 런타임 내려받기**, GPU 점검, Secure Boot | 새로 만듦. 전원은 지금 있는 것을 옮김 |
| 네트워크 | 네트워크, 방화벽, 원격 접속(SSH, RDP), VPN, TLS 와 인증서 | 지금 있는 것을 정리 |
| 시스템 | 저장 공간(디스크, 사용량, 모델 폴더), **부팅**(1절 B6, B7), 업데이트(OS, 드라이버, 커널, Deberopa), 계정, 날짜와 언어, 기본 앱, 서비스, 진단과 로그 | 새로 만듦/정리 |

원칙: 각 설정은 **실제로 동작하는 것만** 넣는다(빈 화면 금지). 데스크톱 설정은 `xfconf-query`/`xrandr`/`pactl` 같은 기존 도구를 호출하는 얇은 층으로 만든다. 새 데몬 API 는 root 권한이 필요한 것(부팅, 디스크)만 추가한다. 기존 AI 페이지의 기능은 하나도 줄이지 않는다.

#### 4.2.1 CUDA 런타임이 눈에 띄지 않는 문제(0.6.2 의 결함)

사실: CUDA 런타임은 **이미지에 들어 있지 않고** 사용자의 컴퓨터가 NVIDIA 저장소에서 직접 받는다(NVIDIA 라이선스가 재배포를 제한하기 때문이다, `licenses.md` 2절). 받기 동작은 0.6.1 에 구현했고 0.6.2 에도 있다. 제어 센터에서는 **시스템 페이지 맨 아래쪽 "업데이트" 묶음의 두 번째 줄**("GPU 가속(CUDA 런타임)", 단추 "NVIDIA 에서 받기")이고, 터미널에서는 `opereta gpu runtime install` 이다. 그런데:

- 시스템 페이지는 모드, 계정, 상시 가동, SSH, 모양을 지나야 나오므로 **스크롤해야 보인다**. 눈에 잘 띄지 않는다.
- 대시보드의 "CUDA 버전" 줄은 **드라이버가 지원하는 CUDA 버전**이지 런타임 설치 여부가 아니다. 이름이 같아 오해를 부른다.
- 런타임이 없어 모델 서버가 CPU 로 도는데도 대시보드, 서버 페이지, 첫 실행 마법사 어디에도 "런타임을 받아야 한다"는 안내가 없다.

수정:

| 번호 | 변경 |
|---|---|
| G1 | 하드웨어 묶음에 **그래픽(GPU)** 페이지를 만들고(AI 대시보드와 서버 페이지에서도 이 페이지로 연결한다) "CUDA 런타임" 상태와 받기 단추를 맨 위에 둔다(상태: 설치됨/없음, 받기 크기, 약관 링크) |
| G2 | GPU 가 있고 런타임이 없으면 **홈과 AI 대시보드에 배너**("GPU 가속을 쓰려면 CUDA 런타임을 받아야 합니다 - 지금 받기")를 띄운다 |
| G3 | 첫 실행 마법사에 "GPU 가속" 단계를 넣는다(약관 확인 뒤 받기, 건너뛰기 가능, 건너뛰면 CPU 로 동작함을 설명) |
| G4 | 대시보드의 "CUDA 버전"을 "드라이버가 지원하는 CUDA"로 이름을 바꾼다 |
| G5 | 서버가 CPU 로 시작되면 서버 페이지 상태에 이유(런타임 없음)와 받기 단추를 보여 준다. 받은 뒤 "서버 다시 시작" 단추를 같이 둔다 |

### 4.3 단계

- C0: **CUDA 런타임 노출(G1~G5)**. 작고 영향이 커서 가장 먼저 한다.
- C1: 구조 개편(사이드바 묶음, 홈, 이 컴퓨터). 기존 기능 이동(AI 페이지 포함, 기능 변경 없음).
- C2: 외관, 디스플레이, 소리, **블루투스**, 키보드. (사용자가 직접 쓰는 빈도가 가장 높다.) 블루투스는 BlueZ 를 D-Bus 로 부르는 얇은 층(`bluez`, `blueman` 은 쓰지 않거나 보조로만)으로 만들고, 어댑터가 없으면 페이지에 이유를 보여 준다. 실제 기기 페어링은 실기에서만 확인할 수 있다
- C3: 부팅, 저장 공간, 기본 앱, 업데이트 통합.
- 각 페이지는 단위 시험(표시 논리), GTK 스모크 시험, 한국어 번역(`.po`)을 갖춘다.

## 5. 데스크톱 디자인: "Xfce 기본과 다르게"

### 5.1 현재 상태의 진단

0.6.2 는 색, 모서리, 단추, 글꼴을 바꿨다. **구성은 그대로다**: 하단 전체 폭 패널, 시작 메뉴 단추, 작업 목록, 알림 영역. 창 틀도 xfwm4 의 평범한 제목 줄 구조다. 그래서 첫인상이 Xfce 다. 사용자가 원한 "macOS Big Sur 와 비슷한 느낌"은 구성 요소(메뉴 막대, 독, 투명, 흐림, 여백)가 만든다.

### 5.3 합성 관리자 교체(picom): 결정 D2

| | xfwm4 내장 합성(현재) | picom + xfwm4(합성 끔) |
|---|---|---|
| 둥근 모서리 | 프레임 이미지의 투명 모서리. 앱 내용은 사각형으로 남아 모서리가 어긋남 | `corner-radius` 로 **모든 창의 최종 모양을 같게** 자른다. 프레임과 내용이 함께 둥글다 |
| 그림자 | 고정된 단순 그림자 | 반경, 오프셋, 색을 설정, 창 종류별 제외 |
| 흐림(블러) | 없음 | 있음(반투명 메뉴 막대, 독, 알림에 필요) |
| 애니메이션 | 없음 | 있음 |
| 위험 | 이미 쓰는 구성 | NVIDIA 와 GLX 백엔드 호환, 일부 앱(전체 화면 동영상, 게임)의 깜빡임, 실기 검증 필요. `xrender` 백엔드로 낮출 수 있다 |

**결정(D2): picom 을 쓴다.** 합성이 시작되지 못하면 W2 의 평면 프레임 모드로 내려간다. NVIDIA 오픈 드라이버와의 실기 동작은 구현 초기에 스파이크로 확인한다(글로벌 백엔드 `glx`, 안 되면 `xrender`). 스파이크가 실패하면 이 결정을 다시 올린다.

### 5.4 단계

- D-M1: 합성 교체와 평면 프레임, 창 효과(2절 문제를 구조로 해결).
- D-M2: 상단 메뉴 막대와 독, 런처.
- D-M3: 파일 관리자, 아이콘, 알림, 로그인 화면, 배경.

램 상한은 U19 로 풀렸으므로 picom 과 plank 는 허용한다.

## 6. 작업 순서(마일스톤)

**릴리스는 한 번(결정 D6: 전부 끝낸 뒤 0.6.3 으로 한 번에).** 마일스톤은 개발과 CI 의 순서이고 각각 별도 커밋과 CI 를 갖는다. 중간 상태는 `phase-6-3` 브랜치에서 검증하고 릴리스하지 않는다.

| 순서 | 내용 | 이유 |
|---|---|---|
| M0 | 사용자에게 1.3.1절 정보를 받는다. 화면 검증 하네스를 저장소에 넣는다(W5). picom, NVIDIA 스파이크 | 원인 확정, 회귀 방지, D2 의 위험 확인 |
| M1 | 부팅(1절 B1~B8) | 설치 후 **OS 에 들어갈 수 없는** 문제라 가장 심각하다 |
| M2 | CUDA 런타임 노출(C0: G1~G5), 단추 순서와 단추 그리기(T0, T1, T2), 창 CSS 조건화와 합성 확인(W1, W2, W4) | 눈에 띄는 결함과 작은 변경 |
| M3 | 제어 센터 구조 개편, 외관, 하드웨어(디스플레이, 소리, 블루투스, 키보드)(C1, C2) | |
| M4 | 데스크톱 디자인(5절): picom 도입, 평면 프레임, 상단 막대, plank, 런처, 아이콘(Papirus), 로그인 화면 | 가장 크고 위험하다 |
| M5 | 제어 센터 부팅, 저장 공간, 기본 앱, 업데이트(C3), 마무리, 문서, 전체 실기 검증 | |

**한 번에 내는 데서 오는 위험**: 한 번에 바뀌는 것이 많아 문제가 생기면 원인 추적이 어렵고, 디자인 개편(M4)이 길어지면 부팅 수정(M1)의 배포가 그만큼 늦어진다. 이를 줄이기 위해 (a) 마일스톤마다 CI 와 컨테이너 스크린샷 비교를 통과시키고, (b) 사용자가 필요하면 `phase-6-3` 의 중간 ISO 를 CI 아티팩트로 받아 실기에서 미리 확인할 수 있게 한다(릴리스는 아니다). 부팅 문제를 지금 겪고 있다면 임시 복구 방법을 별도로 안내할 수 있다.

## 7. 검증 계획과 완료 조건

0.6.2 의 교훈: 가상 환경만으로 "됐다"고 말하지 않는다.

| 대상 | 자동(CI, 컨테이너) | 실기(사용자 PC) |
|---|---|---|
| 부팅 | QEMU: Windows 비슷한 ESP 공존, NVRAM 항목 단언, 복구 | Windows 10 + Opereta 한 SSD 에 설치 → BIOS 목록에 항목 표시, 두 OS 부팅, `opereta boot status` 정상 |
| 창 렌더링 | 컨테이너 스크린샷(합성 켬/끔, 앱 목록) | 실제 GPU(NVIDIA)에서 앱 목록 스크린샷 비교, 합성 상태 표시 |
| 창 단추 | CSS 규칙 존재 시험, 스크린샷 | Firefox, Thunar, 설정 앱 등에서 x, −, + 확인 |
| 제어 센터 | 단위·스모크 시험, 번역 | 각 페이지가 실제 설정을 바꾸는지 직접 조작 |
| 디자인 | 스크린샷 | 사용자의 평가(첫인상) |

**완료 조건**: 위 "실기" 열을 사용자가 확인하거나, 확인하지 못한 항목을 릴리스 노트에 "미검증"으로 적는다. 확인하지 않은 것을 완료로 표시하지 않는다.

## 9. 라이선스와 크기

새로 넣을 후보(`plank`, `picom`, `rofi`, `os-prober`, `ntfs-3g`, `xfce4-windowck-plugin`, `xfce4-docklike-plugin`)는 모두 Debian main 의 자유 소프트웨어이며 대응 소스는 `make sources` 가 릴리스에 함께 올린다. 정확한 라이선스는 구현할 때 `docs/licenses.md` 에 기록한다. 이 문서의 라이선스 언급은 문서 기반 검토이며 법률 자문이 아니다. ISO 크기는 현재 약 1.3 GB 이며 GitHub 릴리스 한도(2 GiB)와의 여유를 확인해야 한다.
